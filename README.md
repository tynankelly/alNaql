# alNaql

**High-Performance Arabic Text Comparison and Matching System**

alNaql is a high performance text reuse detection software with highly configurable, n-gram based text matching system. This software was developed specifically to handle the Arabic script, with particular attention paid to Classical Arabic and Islamic texts. It features special handling of isnads (chains of transmission) and formulaic phrases. The code (and much of this readme file) was largely generated by detailed prompts to claude.ai, section by section (not by "vibe coding"), but has been thoroughly reviewed, edited, updated and tested by the developer. The software architecture, matching strategies, algorithms, and performance optimizes were all created by the developer.

## Quick Start

### 1. Prepare Your Data

**Important**: AlNaql requires XML-formatted input files. Ensure your files:
- Are valid, well-formed XML
- Use UTF-8 encoding
- Contain Arabic text within XML tags

Organize your text files:
```
data/
├── source/          # Primary texts to analyze
│   ├── book1.xml
│   └── book2.xml
└── target/          # Texts to compare against
    ├── target1.xml
    └── target2.xml
```

### 2. Create Configuration File

Copy the default configuration:
```bash
cp default.ini config.ini
```

Edit key settings:
```ini
[paths]
source_dir = "data/source"
target_dir = "data/target"
output_dir = "output"

[generation]
ngram_size = 5
ngram_type = "character"

[matching]
ngram_similarity_metric = "cosine"
min_similarity_threshold = 0.75
```

### 3. Generate N-grams

```bash
./target/release/generate_ngrams config.ini
```

This creates LMDB databases in `ngrams/source/` and `ngrams/target/`.

### 4. Find Matches

```bash
./target/release/find_matches config.ini
```

Results will be in the `output/` directory.

## Usage

### Generating N-grams

The `generate_ngrams` binary creates n-gram databases from your text files.

**Basic usage:**
```bash
generate_ngrams [CONFIG_FILE]
```

**Configuration options (in INI file):**

```ini
[generation]
ngram_size = 5              # Size of n-grams (3-7 typical for character)
ngram_type = "character"    # "character" or "word"
stride = 1                  # 1 = overlapping, >1 = skip n-1 positions
use_parallel = true         # Enable parallel processing
thread_count = 0            # 0 = auto-detect, or specify number

[parser]
remove_diacritics = true    # Remove Arabic diacritics
normalize_arabic = true     # Normalize Alef, Yeh, Heh variants
remove_tatweel = true       # Remove tatweel (kashida)
```

**Output:**
- Creates `.db` directories in `ngrams/source/` and `ngrams/target/`
- Each text file gets its own LMDB database
- Databases include n-grams, prefix indices, and metadata

### Finding Matches

The `find_matches` binary compares n-gram databases to find similar passages.

**Basic usage:**
```bash
find_matches [CONFIG_FILE] [OPTIONS]
```

**Common options:**
```bash
--list-jobs              # Show all comparison jobs and their status
--generate-report        # Generate detailed CSV report
--retry-failed           # Reprocess only failed jobs
--reprocess-completed    # Reprocess all jobs
--resume                 # Resume interrupted processing
--reset                  # Fresh start (deletes previous results)
--self-comparison        # Compare source texts against each other
--job-file <path>        # Use specific job tracking file
```

**Configuration options:**

```ini
[matching]
ngram_similarity_metric = "cosine"    # cosine, jaccard, levenshtein, combined
min_similarity_threshold = 0.75       # Minimum similarity (0.0-1.0)
min_match_length = 50                 # Minimum match length in characters
max_gap_length = 20                   # Maximum gap within a match

clustering_mode = "spatial"           # spatial, chains, or none
grid_cell_size = 1000                 # Grid cell size for spatial clustering

[execution]
processing_mode = "parallel"          # sequential or parallel
max_parallel_comparisons = "auto"     # Number of simultaneous comparisons
parallel_strategy = "smart"           # smart, pooled, or unrestricted
```

**Output formats:**

Controlled by the `[binary_io]` section:
```ini
[binary_io]
output_format = "both"         # binary, json, or both
compress_final_output = true   # Compress final results
```

Output files:
- `output/matches/source_vs_target.bin` (binary format)
- `output/matches/source_vs_target.json` (JSON format)
- `output/state/jobs.db` (job tracking database)

# Advanced Features Documentation

## Banality Detection with Continuous Penalty Scaling

AlNaql includes sophisticated banality detection to identify and down-weight formulaic or boilerplate text in similarity calculations. This prevents common phrases from artificially inflating similarity scores.

### How It Works

**Detection Modes:**

1. **Phrase Mode** (`banality_detection_mode = "phrase"`):
   - Uses user-defined lists of banal phrases and words
   - Matches against `banality_phrases_file` and `banality_words_file`
   - Best for domain-specific formulaic text (e.g., religious formulas, standard greetings)

2. **Automatic Mode** (`banality_detection_mode = "auto"`):
   - Automatically identifies the most common n-grams in your corpus
   - Treats the top N% of n-grams (by frequency) as potentially banal
   - Configurable via `banality_auto_proportion` (default: 5%)
   - Best for discovering corpus-specific common patterns

3. **Disabled** (`banality_detection_mode = ""`):
   - No banality detection applied

### Continuous Penalty Scaling Algorithm

Rather than binary classification (banal vs. non-banal), AlNaql uses continuous penalty scaling:

1. **Calculate Banality Density**: For each text region, calculate what proportion (0.0 to 1.0) consists of banal content
2. **Apply Linear Penalty**: 
   ```
   banality_factor = 1.0 - (banality_density / banality_scale_factor)
   ```
3. **Progressive Reduction**: As banality increases, the contribution decreases linearly:
   - 0% banal → factor = 1.0 (no penalty)
   - 25% banal → factor = 0.5 (with scale_factor=0.5)
   - 50% banal → factor = 0.0 (maximum penalty)
   - Above scale_factor → clamped to 0.0

**Example with `banality_scale_factor = 0.5`:**

| Banal Text % | Banality Factor | Effect |
|-------------|-----------------|---------|
| 0% | 1.0 | Full weight |
| 10% | 0.8 | 20% reduction |
| 25% | 0.5 | 50% reduction |
| 40% | 0.2 | 80% reduction |
| 50%+ | 0.0 | Maximum penalty |

### Configuration

```ini
[matching]
# Detection mode
banality_detection_mode = "phrase"     # "phrase", "auto", or ""

# Phrase mode files
banality_phrases_file = "filters/banalities_phrases.txt"
banality_words_file = "filters/banalities_words.txt"

# Automatic mode settings
banality_auto_proportion = 5           # Top 5% of n-grams
banality_auto_threshold = 80           # Mark as banal if 80% match
auto_banal_batch_size = 10000          # Batch size for detection

# Threshold and scaling
banality_density_threshold = 0.8       # Proportion to mark as banal
banality_scale_factor = 0.3            # Penalty strength (lower = harsher)
```

### Use Cases

- **Religious texts**: Filter out repeated prayers, blessings, and formulas
- **Legal documents**: Down-weight standard clauses and boilerplate
- **Academic texts**: Reduce impact of common citations and references
- **Historical texts**: Handle repeated narrative frameworks

## Isnad Detection for Islamic Texts

For Islamic manuscript analysis, AlNaql provides specialized detection of *isnads* (أسانيد) — chains of transmission that preface hadith and other transmitted texts.

### What Are Isnads?

Isnads are formulaic chains that document the transmission of knowledge, typically following patterns like:

> حدثنا ... عن ... عن ... قال ...  
> (*ḥaddathanā ... ʿan ... ʿan ... qāla ...*)

These chains, while historically important, can dominate similarity scores if not handled specially.

### Detection Method

AlNaql identifies isnad regions based on:

1. **Indicator Words/Phrases**: 
   - Transmission verbs: حدثنا، أخبرنا، سمعت، قال
   - Common words: عن، بن، أبو
   - Common names in chains (limited)

2. **Density Analysis**:
   - Calculates proportion of isnad-related words in a region
   - Marks regions exceeding `isnad_density_threshold` as isnads

3. **Length Requirements**:
   - Only flags regions longer than `isnad_min_length`
   - Prevents false positives from isolated transmission terms

### Configuration

```ini
[matching]
# Isnad detection thresholds
isnad_density_threshold = 0.6          # 60% isnad words to mark region
isnad_min_length = 25                  # Minimum 25 characters

# Word/phrase lists
isnad_phrases_file = "filters/isnad_phrases.txt"
isnad_words_file = "filters/isnad_words.txt"
```

### Phrase File Format

Create `filters/isnad_phrases.txt` with one phrase per line (UTF-8):

```
كنا مع النبي
قال سمعت رسول الله
قال رسول الله
```

### Benefits

- **Separate Content from Attribution**: Compare actual text content without isnad interference
- **Preserve Scholarly Information**: Isnads are tracked but don't dominate similarity scores
- **Flexible Handling**: Can be combined with banality detection for comprehensive filtering

## Word-Weighted Similarity Algorithm

AlNaql's word-weighted similarity algorithm combines sequence matching with traditional similarity metrics, while accounting for text banality.

### Algorithm Components

**1. Longest Common Subsequence (LCS) Similarity**
- Calculates word-level longest common subsequence between source and target
- Formula: `2 × lcs_length / (source_words + target_words)`
- Captures word order and sequence preservation
- Range: 0.0 to 1.0

**2. Base Algorithm Similarity**
- Uses your chosen primary similarity metric (Jaccard, Cosine, etc.)
- Provides set-based or vector-based similarity
- Range: 0.0 to 1.0

**3. Banality Weighting**
- Applies continuous penalty scaling based on formulaic content density
- Reduces LCS contribution for banal text
- Preserves base algorithm contribution

### Calculation Steps

```
1. Calculate base similarities:
   - lcs_similarity = LCS_calculation(source, target)
   - base_similarity = algorithm_calculation(source, target)

2. Assess banality density:
   - banality_density = proportion_of_banal_content(source)

3. Apply banality penalty:
   - banality_factor = 1.0 - (banality_density / banality_scale_factor)
   - banality_factor = max(0.0, banality_factor)  // clamp to 0

4. Weight and combine:
   - weighted_lcs = lcs_similarity × banality_factor
   - final_similarity = (weighted_lcs × lcs_weight) + 
                        (base_similarity × algorithm_weight)
```

### Configuration

```ini
[matching]
# Enable word-weighted similarity
apply_text_weighting = true

# Weighting factors (should sum to 1.0)
lcs_weight = 0.7                       # Weight for LCS component
algorithm_weight = 0.3                 # Weight for base algorithm

# Banality penalty
banality_scale_factor = 0.3            # Penalty strength
```

### Example Calculation

**Scenario:**
- LCS similarity = 0.8
- Base similarity (Jaccard) = 0.9
- Banality density = 40%
- Configuration: `lcs_weight=0.7`, `algorithm_weight=0.3`, `scale_factor=0.5`

**Calculation:**
```
banality_factor = 1.0 - (0.4 / 0.5) = 0.2
weighted_lcs = 0.8 × 0.2 = 0.16
final_similarity = (0.16 × 0.7) + (0.9 × 0.3)
                 = 0.112 + 0.27
                 = 0.382
```

Without banality detection, this would score: `(0.8 × 0.7) + (0.9 × 0.3) = 0.83`

The 40% banal content reduced the score from 0.83 to 0.38, preventing formulaic text from dominating the match.

### When to Use

- **Enable** (`apply_text_weighting = true`):
  - Texts with formulaic patterns
  - Documents requiring word-order sensitivity
  - Cases where sequence matters (literary analysis, chronological texts)

- **Disable** (`apply_text_weighting = false`):
  - Pure set-based matching
  - When order doesn't matter
  - Simple overlap detection

## Multiple Similarity Metrics

AlNaql supports four similarity algorithms, each with different characteristics. You can configure separate metrics for n-gram matching and text-level comparison.

### Available Metrics

#### 1. Jaccard Similarity
**Best for:** Set-based overlap, character n-grams, detecting verbatim reuse

**How it works:**
```
Jaccard(A, B) = |A ∩ B| / |A ∪ B|
```
- Measures intersection over union
- Treats documents as sets of n-grams
- Less sensitive to document length differences
- Fast to compute

**Strengths:**
- Simple and interpretable
- Good for detecting partial overlaps
- Works well with character n-grams
- Robust to length variations

**Weaknesses:**
- Ignores frequency information
- No notion of term importance
- Binary (present/absent)

**Use when:**
- Detecting text reuse or plagiarism
- Working with character-level n-grams
- You want straightforward overlap measurement

#### 2. Cosine Similarity
**Best for:** Vector-based comparison, documents of varying lengths, general-purpose matching

**How it works:**
```
Cosine(A, B) = (A · B) / (||A|| × ||B||)
```
- Measures angle between feature vectors
- Accounts for n-gram frequencies
- Normalized by document magnitude
- Uses precomputed similarity features

**Strengths:**
- Accounts for term frequencies
- Excellent for varying document lengths
- Well-studied and widely used
- Works with weighted features

**Weaknesses:**
- Requires feature computation
- More computationally expensive
- May miss exact overlaps in favor of distributional similarity

**Use when:**
- Comparing documents of different sizes
- You want frequency-weighted matching
- Semantic similarity matters more than exact overlap

#### 3. Levenshtein Distance
**Best for:** Edit distance, detecting small variations, typo tolerance

**How it works:**
- Calculates minimum number of edits (insertions, deletions, substitutions)
- Converted to similarity score: `1.0 - (distance / max_length)`
- Configurable maximum distance threshold

**Strengths:**
- Catches small variations and typos
- Good for OCR'd or noisy text
- Intuitive edit-based interpretation
- Sequence-aware

**Weaknesses:**
- Very expensive for long sequences
- Requires careful threshold tuning
- Can be slow on large texts
- Sensitive to transpositions

**Configuration:**
```ini
[matching]
levenshtein_max_distance = 20          # Maximum edit distance
```

**Use when:**
- Dealing with OCR errors or typos
- Need to detect minor textual variations
- Working with relatively short segments
- Exact matching is too strict

#### 4. VSA (Vector Space Approach)
**Best for:** Semantic similarity, weighted term matching, advanced vector operations

**How it works:**
- Advanced vector space model
- Supports term weighting schemes
- Configurable minimum term weight
- Sophisticated feature combinations

**Strengths:**
- Most sophisticated algorithm
- Flexible term weighting
- Can incorporate semantic information
- Handles complex similarity relationships

**Weaknesses:**
- Most computationally expensive
- Requires careful configuration
- May be overkill for simple tasks
- Needs good term weight tuning

**Configuration:**
```ini
[matching]
vsa_min_term_weight = 0.01             # Minimum term weight
```

**Use when:**
- Maximum sophistication needed
- Have computational resources
- Working with complex text relationships
- Simple metrics aren't sufficient

### Metric Configuration

```ini
[matching]
# Separate metrics for different stages
ngram_similarity_metric = "jaccard"    # For n-gram comparison
text_similarity_metric = "cosine"      # For full text comparison

# Confidence thresholds can differ by stage
ngram_min_confidence = 0.7
initial_text_min_confidence = 0.8
merged_text_min_confidence = 0.7
```

### Choosing the Right Metric

| Use Case | Recommended Metric | Why |
|----------|-------------------|-----|
| Character n-grams | Jaccard | Fast, handles partial overlap well |
| Word n-grams | Cosine | Accounts for word frequencies |
| Varying document sizes | Cosine | Length-normalized |
| OCR'd texts | Levenshtein | Handles typos and errors |
| Plagiarism detection | Jaccard | Clear overlap measurement |
| Semantic matching | VSA | Most sophisticated |
| General purpose | Cosine | Good all-around choice |

### Hybrid Approach

**Recommended configuration:**
```ini
[matching]
# Use Jaccard for fast n-gram filtering
ngram_similarity_metric = "jaccard"

# Use Cosine for final text similarity
text_similarity_metric = "cosine"

# Combine with word-weighted similarity
apply_text_weighting = true
lcs_weight = 0.7
algorithm_weight = 0.3
```

This gives you:
1. Fast initial filtering (Jaccard on n-grams)
2. Sophisticated final scoring (Cosine on text)
3. Sequence-aware weighting (LCS component)
4. Banality handling (continuous penalty)

## Job Tracking and Resume Functionality

AlNaql includes comprehensive job tracking that enables resuming interrupted processes, retrying failed jobs, and monitoring progress across large batch operations.

### How It Works

AlNaql automatically:
1. **Enumerates all comparison pairs** at startup (source × target)
2. **Tracks each job's state** in an LMDB database
3. **Records progress** (start time, end time, status)
4. **Enables resume** from any interruption point
5. **Generates reports** on completion status

### Job States

| State | Description | Next Action |
|-------|-------------|-------------|
| **Pending** | Not yet started | Will be processed |
| **InProgress** | Currently running | May need resume if interrupted |
| **Completed** | Successfully finished | Skip unless `--reprocess-completed` |
| **Failed** | Encountered an error | Retry with `--retry-failed` |

### Command-Line Options

```bash
# View all jobs and their current status
./find_matches config.ini --list-jobs

# Generate detailed CSV report with statistics
./find_matches config.ini --generate-report

# Resume interrupted processing (picks up where it left off)
./find_matches config.ini --resume

# Only process jobs that previously failed
./find_matches config.ini --retry-failed

# Reprocess jobs that already completed
./find_matches config.ini --reprocess-completed

# Fresh start: delete all state and output
./find_matches config.ini --reset

# Use a specific job tracking database
./find_matches config.ini --job-file custom_jobs.db
```

### Job Tracking Database

**Location:** `output/state/jobs.db` (LMDB database)

**Stored Information:**
- Job ID and comparison pair
- Source and target database paths
- Current status
- Start and end timestamps
- Error messages (if failed)
- Output file paths

### Resume Behavior

When you run with `--resume`:

1. **Loads existing job state** from `jobs.db`
2. **Skips Completed jobs** automatically
3. **Retries InProgress jobs** (may have been interrupted)
4. **Processes Pending jobs** normally
5. **Preserves job order** for predictable execution

**Example workflow:**
```bash
# Start processing (interrupted after 50%)
./find_matches config.ini

# Later: Resume from interruption point
./find_matches config.ini --resume
# Only processes the remaining 50%
```

### Selective Processing

**Process only failed jobs:**
```bash
./find_matches config.ini --retry-failed
```
- Processes: Failed jobs only
- Skips: Pending, InProgress, Completed
- Use case: Fix errors after adjusting configuration

**Reprocess everything:**
```bash
./find_matches config.ini --reprocess-completed
```
- Processes: All jobs (Pending + Failed + Completed)
- Use case: Changed configuration and need new results

**Skip existing output:**
```bash
./find_matches config.ini --skip-existing
```
- Default behavior
- Skips jobs with existing output files
- Fast for incremental processing

**Force reprocessing:**
```bash
./find_matches config.ini --no-skip-existing
```
- Processes all jobs even if output exists
- Overwrites existing results

### Best Practices

1. **Use `--list-jobs` frequently** to monitor progress
2. **Generate reports** for batch analysis and debugging
3. **Use `--resume`** for interrupted processes (safest option)

7. **Review error messages** in reports to diagnose failures

## Troubleshooting

### Common Issues

**1. Out of Memory Errors**

```ini
# Reduce parallel comparisons
[execution]
max_parallel_comparisons = 2
min_memory_per_comparison = 4096
```

**2. LMDB Map Size Too Small**

Error: `MDB_MAP_FULL`

```ini
[storage]
map_size_mb = 20480  # Increase size
```

**3. Slow Processing**

- Enable parallel processing: `use_parallel = true`
- Check disk I/O (use SSD if possible)
- Adjust grid cell size for your dataset
- Use `parallel_strategy = "smart"`

**4. Jobs Stuck in InProgress**

```bash
# Resume interrupted jobs
./find_matches config.ini --resume

# Or reset and start fresh
./find_matches config.ini --reset
```

**5. Missing Dependencies**

```bash
# Linux
sudo apt-get install liblmdb-dev

# macOS
brew install lmdb
```
